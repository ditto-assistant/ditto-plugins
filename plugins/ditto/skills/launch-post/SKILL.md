# Launch post

Explain what shipped, why it matters and how it works, accurately enough that an
engineer would sign off and clearly enough that a customer would read to the end.

Use the bundled `ditto-memory` skill for connection, recall and capture rules.

## Gather the facts

Search Ditto for the feature's origin: the problem it solves, the decisions and
trade-offs, measurements and the people involved. Read the actual changes (pull
requests, release notes, docs) when they are available. Confirm what is really
live, for whom, and with what limits. Do not announce what has only been merged,
or present a plan as shipped.

## Write it

Pick one reader (customer, developer or investor) and write for them.

1. **Headline:** the user-visible outcome, not the internal project name.
2. **Opening:** the problem in the reader's words and what is now possible.
3. **How it works:** the essential mechanism, with one diagram or table if it
   genuinely explains something.
4. **Proof:** real numbers, examples or quotes with their conditions, never
   invented ones.
5. **Limits and what is next:** honest availability, constraints and roadmap
   claims the user has approved.
6. **Call to action:** how to try it.

Keep claims checkable. Mark anything you could not verify for the user to
confirm. Match the user's past posts for voice when Ditto has them.

## Deliver

Return the draft for review, plus a short version for social posts and a one-line
changelog entry when useful. Publishing, posting or emailing are separate
actions: do them only when the user asks, through a connected tool. Offer to save
the final post and its sources to Ditto.
